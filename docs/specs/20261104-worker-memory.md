# worker 内存封顶：回测面板流式读、空闲回收、限时退出

- 状态：draft
- 创建：2026-11-04
- 相关：D3（worker 重启不自动重跑）、D60（写库时不跑回测）、D76（行情仓升级不在启动时做）、DEPLOY.md「worker 内存预算」

## 背景

2026-11-03 晚上演示站整机卡死近 40 分钟（20:33 → 21:12 冷启动）。演示站是 2 核、3.6 GB、2 GB swap 的机器，
上面还有十来个别的服务；当晚 20:00–20:33 可用内存只有 650–770 MB（DEPLOY.md 按约 1.2 GB 空闲写的预算），
其中 worker 在 17:30 的 A 股更新做完后一直占着约 570 MB。

worker 日志与应用库 `jobs` 表对得上的经过：

- 20:23:36 港股第 2 次自动重跑开始，20:32:45 因「没成交的股票远多于平时」失败（写进去的日线留在约 8.8 MB 的 WAL 里，没有 CHECKPOINT）。
- 20:30:42 有人提交了一次回测（趋势跟踪·均线上行：主板、月度换仓、前 20、2018-01-01 起），**按 D60 排队等更新**，20:32:45 更新一结束就开始；
  20:32:58 报 DuckDB `Out of Memory Error (366.2 MiB/366.2 MiB used)`。20:33:02 重试同样报错。
- 20:33:11 又提交两次（区间改成 2020 年起、以及 2018 年起），第一个开始跑，约 1 分钟后整机卡死（swap 抖动，内核没有杀进程）。
- 21:12:56 冷启动，worker 打开行情仓用了约 27 秒；21:13:23 把卡死前在跑的那个标成失败，接着认领还在排队的 2018 年起那次回测；
  21:13:56 pm2 量到 RSS 1,502,257,152 字节（> 900M）要重启它，SIGINT 后 10 秒没退出（`failed to kill`），被 SIGKILL。
- 21:14:08 第二次启动，同一份 WAL 照样重放，RSS 一直在 140–290 MB——**启动、重放 WAL、标失败都不是 1.5 GB 的来源，是那次回测**。

## 原因

1. **回测的价格面板整表读进 JS**（主因）。`buildSimInput` 用 `runAndReadAll` + `getColumnsObjectJS` 读「入选过的股票 × 区间内交易日」的日线：
   DuckDB 先把整份结果物化在内存上限里，再在主线程转成整表的 JS 数组（每行一个代码字符串、一个日期字符串、六七个数），再 `map` 一遍。
   趋势类策略换手高，9 年里入选过两千多只，面板五百多万行。合成行情仓复现（Linux x64，2201 只 × 约 2200 天）：
   `DUCKDB_MEMORY_LIMIT=384MB` 时 worker 7 秒到 1.48 GB、峰值 3.59 GB、跑完一直占着 2.5 GB；
   `256MB` 时直接报和线上一样的 `Out of Memory Error ... (244.0 MiB/244.1 MiB used)`。
2. **面板查询把整张因子表做连接**：`LEFT JOIN factors_daily` 没有按股票和日期先筛，连接要把上千万行装进 DuckDB 的内存上限，
   这就是 20:32:58、20:33:07 两次 OOM（同一查询先筛后连，192MB 下就能跑完）。
3. **退出等不到**：主线程在同步的整表转换里（加上 swap），信号处理排不上队；老代码 1.7 GB 时收到 SIGINT 要 21.9 秒才退出（pm2 10 秒就 SIGKILL）。
   被 SIGKILL 的 worker 留下没并回的 WAL 和「运行中」的任务。
4. **空闲时不还内存**：DuckDB 不会自己归还缓存，夜间更新之后 worker 一直占着接近上限的内存；转交给回测线程的面板要等线程下次 GC。
5. 已经排除的：DuckDB 的 `memory_limit`、`threads`、`preserve_insertion_order` 本来就在打开时通过配置给（不是打开后再 SET），
   WAL 重放在上限之内；`temp_directory` 用默认的 `market.duckdb.tmp/`（卡死后留下的那个目录就是它）。回测与夜间更新本来就不同时跑（D60），
   当晚的回测都是等更新结束才开始的。

## 方案

- **面板逐块流式读**：`Warehouse.streamColumns` 在单独的连接上 `stream` 查询，每块约 2048 行交给回调，JS 里一次只留一只股票的行；
  因子表先按同样的股票与区间筛好再连接。面板逐格写进的值、顺序都和原来一样，输入指纹不变（合成库新旧两版逐字节相同）。
- **面板上限** `BACKTEST_PANEL_MB`（默认 320，演示站建议 256）：读的过程中累加面板字节数，超了停止读，这次回测报
  「这次回测要装进内存的行情太多（N 只股票、M 个交易日，超过 X MB 的上限），缩短回测区间、降低换仓频率或缩小股票池后再试」。
  只管回测、复核、重跑（`rebuildInput`）；结算的窗口短，不设。
- **单独排的结算也挡回测**（`COMPUTE_EXCLUSIVE` = 写行情仓的任务 + `settle`）：结算给每个跟踪组装面板、跑模拟，和回测同时跑峰值叠加。
  夜间结算本来就在 etl 任务里，这一条管的是管理页手动排的结算。简报、事件数据回填照旧不挡。
- **空闲回收**：两条道都空下来 30 秒后 `CHECKPOINT`（WAL 并回主文件，被杀之后不用重放），把 DuckDB 内存上限临时降到 32MB 再恢复（逐出缓存），
  换掉跑过任务的回测线程（面板随旧线程释放）。回收期间来的读写先等它做完；有读写在执行时这次不回收。
- **限时退出**（`shutdown.ts`）：停认领与调度 → 关内部接口 → 终止回测线程 → 打断行情仓上在跑的查询 → 等任务收尾（≤ 2 秒）→
  CHECKPOINT 并关库（≤ 3 秒）→ 关应用库 → 退出码 0；8 秒兜底强退，退出中再收到信号立刻退出。被打断的任务、回测记「worker 重启」，
  和下次启动的 recoverStale 一致。
- **文档**：DEPLOY.md「worker 内存预算」按实测重写，`.env.example` 加 `BACKTEST_PANEL_MB`；`scripts/backfill-full.sh` 可以用
  `BACKFILL_MEMORY_LIMIT` 给停着 worker 的回填多一些内存。`max_memory_restart` 保持 900M（见 D110）。

## 决策记录

- **D110 worker 的内存每一块都有上限，空闲时还回去，退出赶在 SIGKILL 之前（2026-11-04）。**
  峰值 = DuckDB 上限 + 面板上限 + 线程堆上限 + 约 150 MB，都由配置封顶；大结果一律逐块流式读，主线程不再整表转数组。
  面板超上限时拒绝这次回测而不是硬跑：在和别的服务共用的小机器上，一次回测把整机拖进 swap 的代价远大于让用户缩短区间。
  单独排的结算并进「和回测互斥」的任务（修正 D60 里「结算不写行情仓，不用等回测」）。
  `max_memory_restart` 不降：pm2 每 30 秒才量一次，挡不住几秒内的尖峰（这次就是），只兜慢慢涨上去的情况；
  降到参考配置的峰值附近反而会在正常的大回测、夜间更新中途重启 worker。
  放弃的方案：给主线程加 `--max-old-space-size`（流式读之后主线程堆只有几十 MB，但夜间更新的堆没量过，设低了会让更新崩溃重启）；
  `MALLOC_ARENA_MAX=2`（实测峰值和空闲都没有明显好处）；空闲时退出进程让 pm2 拉起（重开 5.5 GB 的库要十几秒，期间内部接口不可用）；
  分批按股票读面板（每批都要扫一遍日线表，慢几倍）。

## 验收标准

1. 合成行情仓上同一次回测，流式读前后输入指纹相同；`DUCKDB_MEMORY_LIMIT=256MB` 下跑得完（老代码 OOM）。
2. 面板超过 `BACKTEST_PANEL_MB` 时回测报「行情太多」，worker 内存不越过上限。
3. 单独排的结算排队或在跑时，回测排队并显示「行情正在更新，回测会在更新完成后开始」；结算等在跑的回测结束再开始。
4. 两条道空闲 30 秒后 worker 的 RSS 回落（DuckDB 缓存、回测线程）；回收期间来的请求照常返回。
5. 回测跑到一半收到 SIGINT：1 秒内退出、退出码 0、没有留下 `market.duckdb.wal`，任务与回测记「worker 重启」。
